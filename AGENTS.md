# Сведения для агентов (AI / автоматизация)

Репозиторий **MasterProject** (AI Doctor — анализ ВНЧС по КЛКТ).

## С чего начать

1. **[README.md](README.md)** — продукт, глоссарий, быстрый старт, HTTP API, troubleshooting.
2. **[MLService/README.md](MLService/README.md)** — пайплайн ML, инструменты, карта подпапок.

## Спецификации и порядок разработки

- Начните с [общей карты](docs/spec/README.md) и правил затронутого компонента: [Backend](Backend/docs/spec/README.md), [MLService](MLService/docs/spec/README.md), [iOS](iOSApp/docs/spec/README.md).
- `docs/spec/` компонента задаёт поведение и приёмку, `docs/ai/` описывает текущую реализацию. Общие принципы, термины и шаблоны хранятся только в корневом `docs/spec/`.
- Прочитайте правило, соседние приёмочные сценарии и применимые дополнения компонента. Выберите [порядок разработки](docs/spec/conventions/README.md) по конкретному поведению: от спецификации к коду либо сначала код. Новое поведение в уже описанном интерфейсе при втором порядке требует дополнения в том же PR; оно не может переопределять правило.
- Для локальной правки достаточно тематического правила и приёмки; отдельные spec/plan нужны при существенном дизайне или координации, а не для каждой задачи. Адаптируйте пути из skills к каталогам с единственным README.md. Сохраняйте ID, якоря и одного владельца правила.
- Известное отсутствие согласованного поведения — GAP; неизвестный продуктовый выбор — OQ. Не подгоняйте требования под ошибку кода, не выдавайте описанный тест за выполненный. Существенный вопрос, влияющий на реализацию, разрешайте до зависимой правки; уже данное поручение не требует повторного подтверждения.
- При изменении границы проверьте [соглашения](docs/spec/integration/README.md) и обе стороны. Для ML до запуска заполните [протокол](MLService/experiments/template/README.md): данные/группы пациентов, baseline, метод выбора модели, метрики и ресурсы. Пропуск не означает нормальный класс; серия не заменяет patient ID.
- Обновляйте инженерные сведения и реальные связи с проверками. Ход работы, команды и результаты храните в PR, исследовательские результаты — в протоколах; не превращайте постоянную спецификацию в журнал сессии.
- Для проверки документов: `python3 scripts/check_specs.py --self-test`, `python3 scripts/check_specs.py`, `git diff --check`. Изменение документации не требует обучения, запуска сервисов или сборки приложения.
- Сохраняйте существующие незакоммиченные изменения; приватные данные и секреты не добавляйте в Git ради полноты документации.

## Правила документации (обязательно)

- В **каждом каталоге** в git должно быть **либо ровно один** файл **`README.md`**, **либо ни одного** файла с расширением **`.md`**.
- **Исключение для корня репозитория:** допускается второй файл **`AGENTS.md`** (этот файл) — правила для агентов и политика доков.
- Длинные справки, не помещающиеся в один README каталога, выносите в **`.txt`** или в код/комментарии; не плодите второй `.md` рядом с README.
- Для **текущей реализации источник истины — исходники** (`AnalysisController.swift`, `routes.swift`, `app.py`, эндпоинты клиента). Согласованные правила задают целевое поведение; их расхождение с реализацией записывается явно.
