# Анализ DICOM-серии

Форматы и значения на границе определяет [интеграционный контракт клиента](../../integration/README.md).
Оценка реализации находится отдельно в [трассировке](../../traceability/README.md).

<a id="fr-ios-choose-series"></a>
### FR-IOS-CHOOSE-SERIES — Выбор серии

Пользователь должен иметь возможность выбрать одну папку через системный выбор файлов.
В серию включаются её непосредственные файлы с расширением `.dcm` без учёта регистра; вложенные папки не обходятся.
Клиент должен показать число выбранных файлов и предоставить просмотр их имён.
Выбор не запускает передачу автоматически.
Пустая папка, отказ доступа и ошибка чтения должны давать различимые сообщения и не создавать новую готовую серию.

Приёмка: [TC-IOS-SERIES-SELECTION](#tc-ios-series-selection).

<a id="tc-ios-series-selection"></a>
### TC-IOS-SERIES-SELECTION — Выбор папки

Предусловие: папка содержит непосредственные `.dcm` и `.DCM`, иной файл и вложенную папку с DICOM.
Действие: выбрать папку; затем проверить пустую папку, отказ доступа и ошибку чтения.
Наблюдаемый итог: выбраны только непосредственные DICOM-файлы, показаны число и доступные имена; передача не начата; неуспешный выбор не объявлен готовым.

<a id="fr-ios-complete-series"></a>
### FR-IOS-COMPLETE-SERIES — Явный запуск и целостность выбора

Анализ запускается явным действием пользователя только для непустой серии.
Одна операция должна использовать тот набор файлов, который был выбран при её запуске.
Клиент не должен начинать вторую операцию анализа, пока текущая выполняется.
Изменение выбора не должно менять файлы уже начатой операции или приписывать её результат новой серии.
Если хотя бы один выбранный файл нельзя прочитать, клиент должен сообщить об этом и не отправлять усечённую серию как полную.

Приёмка: [TC-IOS-COMPLETE-OPERATION](#tc-ios-complete-operation).

<a id="tc-ios-complete-operation"></a>
### TC-IOS-COMPLETE-OPERATION — Полнота и один активный анализ

Предусловие: выбрана непустая серия; один из файлов можно сделать недоступным перед чтением.
Действие: запустить анализ, попытаться запустить второй и изменить выбор; отдельно запустить с недоступным файлом и пустым списком.
Наблюдаемый итог: активная операция использует исходный набор, второй запуск не начинается, результат относится к исходной серии; недоступный файл и пустой список не приводят к загрузке неполной серии.

<a id="fr-ios-task-identity"></a>
### FR-IOS-TASK-IDENTITY — Передача серии и идентичность задачи

Клиент должен передавать все файлы выбранной серии в одной операции загрузки по общему контракту с Backend.
После успешного принятия загрузки клиент должен использовать идентификатор задачи, возвращённый Backend.
Ответ с отсутствующим или некорректным идентификатором не считается принятием задачи.
Дальнейшие ответы должны относиться к той же задаче; несоответствие идентификатора — ошибка протокола.
Сбой передачи не должен показываться как успешное завершение анализа.

Приёмка: [TC-IOS-TASK-IDENTITY](#tc-ios-task-identity).

<a id="tc-ios-task-identity"></a>
### TC-IOS-TASK-IDENTITY — Принятие и идентификатор

Предусловие: все файлы доступны, принимающая сторона управляемо возвращает корректный ответ, некорректный идентификатор либо отказ.
Действие: запустить загрузку и проверить дальнейшие обращения; вернуть ответ другой задачи.
Наблюдаемый итог: переданы все выбранные файлы, используется возвращённый идентификатор; некорректный или чужой идентификатор и отказ дают ошибку, без объявления успеха.

<a id="fr-ios-terminal-outcome"></a>
### FR-IOS-TERMINAL-OUTCOME — Ожидание терминального исхода

После принятия задачи клиент должен получать её состояние через согласованный интерфейс Backend.
Нетёрминальное состояние означает продолжение ожидания; оно не является готовым результатом.
Терминальный успех разрешает отображение результата только после проверки его состояния и данных.
Терминальная ошибка завершает ожидание и отображает причину, если Backend её предоставил.
Неизвестное состояние должно сообщаться как несовместимость протокола, а не превращаться в бесконечное ожидание.
Правило прекращения ожидания по времени требует решения [OQ-IOS-WAITING-POLICY](../../open-questions/README.md#oq-ios-waiting-policy).

Приёмка: [TC-IOS-TASK-STATES](#tc-ios-task-states).

<a id="tc-ios-task-states"></a>
### TC-IOS-TASK-STATES — Состояния задачи

Предусловие: принята задача; Backend последовательно возвращает согласованные нетёрминальные состояния и терминальный исход.
Действие: проверить успех, ошибку с причиной, неизвестное состояние и нетёрминальный ответ при получении результата.
Наблюдаемый итог: обращения идут по общему контракту, ожидание продолжается только для допустимых состояний; проверенный успех отображается, ошибка сохраняет причину, неизвестное или несогласованное состояние даёт ошибку протокола.
Проверка численного предела ожидания определяется после решения OQ-IOS-WAITING-POLICY.

<a id="fr-ios-validate-localization"></a>
### FR-IOS-VALIDATE-LOCALIZATION — Проверка локализации

Клиент должен проверить данные локализации до обращения к отдельным координатам.
Предоставленный размер объёма содержит ровно три положительных целых размера; центр — ровно три конечных числа; границы области — ровно шесть целых координат.
Порядок осей и единицы должны соответствовать общему контракту.
Ошибка разбора предоставленного блока отличается от отсутствующего блока.
Некорректный блок не должен вызывать аварийное завершение, скрываться под видом отсутствия данных или подтверждать успешную локализацию.
Проверка геометрических границ должна следовать согласованной семантике координат, а не предположению о способе индексирования.

Приёмка: [TC-IOS-INVALID-LOCALIZATION](#tc-ios-invalid-localization).

<a id="tc-ios-invalid-localization"></a>
### TC-IOS-INVALID-LOCALIZATION — Некорректная локализация

Предусловие: ответ успешной задачи содержит корректные координаты либо повреждённый блок.
Действие: проверить ошибочный вложенный JSON, массивы длиной 0/2 вместо 3 и 5 вместо 6, неположительный размер и нечисловой центр; затем валидный ответ.
Наблюдаемый итог: некорректные значения дают различимую ошибку данных без аварии и ложного успеха; корректные значения сохраняют сторону, оси и единицы общего контракта.

<a id="fr-ios-present-localization"></a>
### FR-IOS-PRESENT-LOCALIZATION — Представление результата

Клиент должен отдельно обозначать левый и правый ВНЧС, порядок осей центра и границы области.
Размер объёма отображается только при наличии проверенного значения.
Для отсутствующей стороны клиент должен явно показывать отсутствие локализации; нулевые координаты не подставляются.
Если терминальный ответ не содержит локализации обеих сторон, интерфейс должен сообщать об отсутствии данных, а не создавать впечатление найденных суставов.
Отображение отсутствующих данных — защитная обработка неполного ответа, а не признание частичного анализа успешным; политика такого результата остаётся [открытым решением Backend](../../../../../Backend/docs/spec/open-questions/README.md#oq-be-result-completeness).
Числовая локализация не должна представляться как клинический диагноз, классификация положения или результат сегментации.

Приёмка: [TC-IOS-PARTIAL-RESULT](#tc-ios-partial-result).

<a id="tc-ios-partial-result"></a>
### TC-IOS-PARTIAL-RESULT — Полный и частичный результат

Предусловие: получены полный терминальный ответ и неполные терминальные ответы с одной стороной или без локализации.
Действие: отобразить каждый ответ с предоставленным размером объёма и без него.
Наблюдаемый итог: стороны и оси подписаны, присутствующие значения отображаются, отсутствующая сторона обозначена явно; отсутствие обеих сторон объяснено; диагноз и другие неподдерживаемые выводы не появляются.

<a id="fr-ios-operation-feedback"></a>
### FR-IOS-OPERATION-FEEDBACK — Состояние операции и ошибки

При запуске нового анализа предыдущий результат должен перестать представляться как результат текущей операции.
Во время чтения, передачи или ожидания клиент должен показывать, что операция продолжается.
После успеха либо ошибки признак выполнения снимается, а пользователь получает наблюдаемый итог.
Ошибка выбора, доступа, передачи, обработки и ответа должна объяснять, на каком этапе операция остановилась.
Доступная причина ошибки обработки должна сохраняться до пользовательского сообщения; технические подробности не должны заменять понятное описание.
После ошибки пользователь может снова выбрать серию и явно начать анализ.

Приёмка: [TC-IOS-ERROR-RECOVERY](#tc-ios-error-recovery).

<a id="tc-ios-error-recovery"></a>
### TC-IOS-ERROR-RECOVERY — Итог и повторный запуск

Предусловие: на экране есть результат предыдущей операции.
Действие: начать новый анализ; отдельно завершить его успехом, отказом чтения, сетевой ошибкой, серверной ошибкой и ошибкой ответа; после ошибки повторить запуск.
Наблюдаемый итог: прошлый результат не выдаётся за новый; состояние выполнения видно и снимается после исхода; ошибка объясняет этап и доступную причину; явный повторный запуск доступен.
