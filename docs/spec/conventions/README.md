# Правила ведения спецификаций

## Структура и владельцы

В каждом из `Backend`, `MLService`, `iOSApp` каталог `docs/spec/` содержит свой индекс, темы `functional/`, общие для компонента требования `nonfunctional/`, интеграцию, вопросы/пробелы, прослеживаемость и дополнения `patches/`. Инженерные факты, пути, поля, классы и изученное покрытие находятся в `docs/ai/`. Общие принципы, термины и шаблоны существуют в корневом `docs/spec/` в одном экземпляре.

Раздел темы содержит назначение, применимость и владельца данных, правила, ошибки/пустые результаты и приёмку «Если / Когда / Тогда». Он должен быть понятен без чтения кода. Ссылка на реализацию подтверждает наблюдение, но не заменяет правило. Точное поле допустимо в правиле, если от него зависит смысл публичного контракта.

Статус намерения обозначается в тексте: поддерживаемый контракт, согласованная цель либо предложение. Неподтверждённое продуктовое решение не становится согласованным от наличия ветки кода. Никакие исследовательские пороги не придумываются ради заполнения документа.

## ID и приёмка

Префиксы владельцев: `BE`, `ML`, `IOS`; `MP` — только общие соглашения системы. Виды: `FR` — функциональное правило, `NFR` — общее ограничение, `TC` — приёмка, `INT` — соглашение границы, `GAP` — установленный пробел, `OQ` — вопрос владельцу, `PATCH` — дополнение. После префикса использовать описательный суффикс темы; общего счётчика задач нет.

Определение — заголовок с ID и явным HTML-якорем в нижнем регистре. Например, `### FR-ML-LABEL-PLANE — Проверять плоскость метки` и `<a id="fr-ml-label-plane"></a>`. У ID один владелец и одно определение; ссылки могут повторяться. При перемещении сохранить ID, якорь и обновить ссылки. Не переиспользовать ID для другого смысла.

Каждое FR/NFR ссылается на один или несколько TC; определение TC находится рядом в той же теме. В `traceability/` указывается существующая автоматизация и её пределы либо её отсутствие. Центральный индекс остаётся навигационным: не нужно регистрировать каждую локальную правку во всех таблицах. Применимость теста проверяется по assertions, а не имени файла.

## Два порядка разработки

**От спецификации к коду.** Если правило уже задаёт затронутое поведение, сначала проверить поручение на соответствие ему. Восстановление действующего правила требует кода и релевантной проверки, без пустой правки текста. Для изменения намерения уточнить существенные вопросы и изменить правило с приёмкой в том же или более раннем PR относительно реализации. Отдельный PR спецификации необязателен; разделение коммитов допустимо.

**Сначала код.** Если конкретное поведение ещё не задано, реализация и проверка могут идти обычным PR. Когда новый наблюдаемый результат добавляется внутри уже описанного интерфейса или сценария, в тот же PR включается самостоятельное дополнение из `patches/<topic-change>/README.md`. Для интерфейса, ещё не охваченного правилами, такое дополнение необязательно; последующее принятие поведения в спецификацию — отдельное решение, без установленного срока. Внутренняя техническая правка без нового поведения дополнения не требует.

Ни один порядок не разрешает переопределять правило дополнением или откладывать разрешение нового противоречия. При конфликте правил сначала выяснить намерение. Поле или термин в глоссарии само по себе не означает, что для поведения уже есть правило. При затрагивании двух компонентов каждый владелец обновляет свою часть, а соглашение границы связывает их.

## Дополнения и существенные функции

Дополнение содержит область действия и ссылку на основное правило, новое условие/результат, собственные ID `PATCH-<owner>-...` и `TC-PATCH-<owner>-...`, ошибки/границы и доказательство проверки либо названный пробел покрытия. Это долговечное правило, а не отчёт PR. Оно не нуждается в записи в общем журнале. Перенос в тематическую главу необязателен; при переносе сохраняются ID/якоря, обновляются ссылки и удаляется заменённое дополнение.

Для небольшого изменения достаточно правила и соседней приёмки. `docs/spec/features/<topic>/README.md` создаётся, когда изменение затрагивает несколько тем или требует отдельного согласованного решения. Технический план можно выделить в `features/<topic>/plan/README.md`; список зависимых задач — в его раздел. [Шаблоны](../templates/README.md) общие, пустые документы ради процесса не создаются.

## Пробелы и вопросы

GAP содержит правило/ожидание → текущую реализацию → последствие → доказательство. Подтверждённое отсутствие поведения не требует повторного решения о том, нужно ли соблюдать уже согласованное правило. OQ содержит конкретный неизвестный выбор, последствия вариантов и `Ответ: ожидается решение владельца`. После ответа обновить правило, приёмку и инженерные сведения; не оставлять установленный факт вопросом.

В интеграционных сведениях различаются согласованность `Aligned / Divergent / Unverified / N/A` и реализация `Implemented / Implemented-partial / Divergent / Not-implemented / Retired`. Они не обозначают успешный запуск. Источники: код владельца/потребителя, контракт, существующий тест или явное согласованное намерение. Отчёт фактического запуска хранится в PR или протоколе эксперимента.

## Проверка и завершение

До завершения связать изменённые правила с приёмкой, проверить обе стороны затронутой границы, обновить инженерные сведения и выполнить достаточные проверки. В PR указать пути/ID, команды, результаты и что не выполнялось. Для документов достаточно `python3 scripts/check_specs.py --self-test`, `python3 scripts/check_specs.py` и `git diff --check`; смысл требований проверяется ревью.

В спецификации не включаются история чата, текущий ход ветки, одноразовые даты запусков и снимки окружения. Для экспериментов используется [протокол ML](../../../MLService/experiments/template/README.md); численные результаты не становятся постоянными гарантиями компонента автоматически.
